# 願相(隠れ相)検出エンジン ロードマップ

## この機能は何をしていて、何をしていないか(正直な現状整理・更新版)

ユーザー提示の「願相検出プロンプト」は、本来は**画像認識AI(機械学習)**が
担う仕事(画像の中から顔らしいパターンを自動検出する)を前提にしている。
これを3つの層に分けて実装を進めている:

```
検出層(自動・ヒューリスティック ✅実装済み) → 解釈層(ルールベースで自動化 ✅実装済み)
```

- **解釈層**(`app/hidden-face-engine.js`): 位置・向き・種類・数から
  意味づけ文を組み立てる部分。完全に実装・動作確認済み。
- **検出層**(`app/hidden-face-detector.js`, 今回追加): 画像から実際に
  「暗い点(ほくろ等)のペア+その下の暗い線(しわ・口)」の組み合わせを
  自動で探す部分。**機械学習ではなく、古典的な画像処理
  (閾値処理+連結成分ラベリング+幾何マッチング)で実装した**。
  これにより、**ラベル付き学習データが0件でも動く自動検出**が実現できた
  (ユーザーの「ラベル付き画像データなしでも点と線の組み合わせで顔に
  見える可能性の追求を実装したい」という要望への回答)。

以前のセッションでは「人が3点タップでマーキングする」だけだったが、
今回はその手前に「自動で候補を提案する」ステップを追加した:

1. 画像アップロード
2. **「自動検出する」ボタン**: 縮小した画像をアルゴリズムで解析し、
   点+線のパターン候補を最大5件、スコア順にリスト表示
3. 候補から「採用する」を押すと、3点マーキングに自動反映される
   (その後、必要なら手動で微調整も可能)
4. 「解析する」→スコア・向き・意味づけを表示
5. 「学習データとして保存」→将来の精度向上・ML化のための記録として蓄積

## 検出層(`app/hidden-face-detector.js`)のアルゴリズム詳細

DOMに依存しない純粋関数のみで構成(Node上で合成ピクセルデータを使い
ユニットテスト済み: 意図的に描いた「二点+線」パターンが正しく検出され、
ノイズ画像や無地の画像では検出されないことを確認済み)。

1. **`detectDarkBlobs()`**: 画像をグレースケール化し、画像全体の
   平均輝度−標準偏差を閾値として「暗い画素」を判定。4近傍の
   幅優先探索(フラッドフィル)で連結成分(暗い塊=ほくろ・瞳等の候補)を
   検出し、大きさでノイズ・巨大な影を除外する。
2. **`detectDarkRunInRegion()`**: 指定した矩形範囲内で、最も長い横方向の
   暗い画素の連なりを探す(しわ・口の候補)。ほくろよりやや緩い閾値を
   既定値にしている。
3. **`findFaceCandidates()`**: 検出した暗い塊のペアを総当たりし、
   「目の間隔として妥当な距離」「高さがある程度そろっている」ものだけを
   残し、そのペアの下の領域に口候補となる線があるかを探す。見つかった
   組み合わせを`HiddenFaceEngine.computeFaceLikenessScore()`でスコア化し、
   スコア順に上位候補を返す。

`app/app.js`側では、アップロードされた画像を長辺240pxに縮小した
オフスクリーンcanvasに描画し、`getImageData()`で取得した画素データを
この検出関数に渡している(処理負荷を抑えるための縮小)。

## 精度についての正直な課題(ユーザー指摘の通り)

ユーザーの指摘通り、**ほくろ・しわを正確に見るには、まだ精度が足りない**。
現状の実装は「グローバルな明度閾値」という最も単純な方式で、以下のような
誤検出・見逃しが起こりうる:

- 照明にムラがある写真では、影の濃い部分が誤って「ほくろ」として検出される
- 髪の毛、眉、鼻の穴、瞳孔なども暗い塊として拾われてしまう
- 薄いしわは背景の明度によっては検出されない(逆に濃い影は過検出される)

### 精度向上のための具体的な次の一手(1〜4は実装済み・更新)

1. **局所適応閾値(✅実装済み)**: 画像全体の平均ではなく、各画素の近傍
   (積分画像で高速に計算。既定半径は画像短辺の約8%)の明度を基準に
   閾値を決める(適応的二値化)。照明ムラへの耐性が上がる。
2. **肌色マスキング(✅実装済み)**: YCbCr色空間の経験的な範囲判定で
   肌色らしい画素の外接矩形(+15%程度の余白)を求め、点・線の検索範囲を
   その中に限定する。髪・服・背景の誤検出を抑える。肌色画素が少なすぎる/
   多すぎる(判定が信頼できない)場合は自動的に画像全体へフォールバック
   する安全弁つき。
   - **正直な限界**: 単純なYCbCr範囲判定は、写真の光源・色味・肌の色みの
     違いによって外れやすいという既知の限界がある(特定の肌の色みだけ
     検出精度が落ちる、といった偏りが起こりうる)。フォールバックを
     必ず備えているのはこのため。今後、実写真での検証(下記優先事項1)
     で偏りが大きいと分かった場合は、マスキングの重み付けを弱める、
     または無効化オプションを目立たせるなどの対応を検討する。
3. **平滑化(✅実装済み)**: 検出前にボックスブラー(横→縦の2パス、
   既定半径1px)をかけ、ノイズ由来の小さな誤検出を減らす。
4. **候補の形状フィルタ(✅実装済み)**: 点候補は外接矩形に対する
   充填率(既定0.35以上=丸み・塊らしさ)とアスペクト比(既定3.0以下)で
   毛髪等の細長い塊を除外。線候補は隣接行に重なりのある暗い連なりが
   あるもの(線としての連続性)を優先し、無い場合のみ単一行のベスト
   候補にフォールバックする。
   - 合成データでのユニットテスト(`tests/hidden-face-detector.test.js`)
     で、肌色領域外の暗い点が除外されること・肌色判定不能画像では
     全体探索にフォールバックすること・毛髪状の細長い塊が点候補から
     除外されることを確認済み(`npm test`で実行可能)。純粋なランダム
     ノイズ画像でも一定数の誤検出は残る(合成データでの参考値として
     テスト内にログ出力しているのみで、厳密な閾値は設けていない)。
5. **最終的にはML化**: 上記のヒューリスティックをどれだけ磨いても
   限界はあるため、`ninso.gansou_samples.v1`に蓄積されるデータが
   一定量に達したら、実際に学習させたモデルに置き換えるのが本筋。
   その際も解釈層(`hidden-face-engine.js`)はそのまま使い回せる設計に
   してある。技術スタックの具体案は下記「将来、本当にAIモデル化する
   場合のロードマップ」を参照。

## 抽象相・自動解析判定エンジン(JSON入出力版)

ユーザーから提示された、より汎用的な仕様(画像解析AI+人間選別
[Human-in-the-Loop]によって確定された検出データJSONを受け取り、十二宮の
考え方で解釈する)を`buildAbstractGansouReport()`として実装した。

### 3段階ワークフローとこのアプリの対応

| ユーザー提示のワークフロー | このアプリでの対応 |
|---|---|
| 1. 自動抽出ステップ(画像解析AIが候補にフラグを立てる) | `hidden-face-detector.js`の`findFaceCandidates()`(「自動検出する」ボタン) |
| 2. 人間選別ステップ(ユーザーが候補を確定) | 「採用する」ボタン(現状はマーキング形式の内部データとして保持) |
| 3. 自動解析ステップ(本エンジンの実行) | `buildAbstractGansouReport()`(「抽象相JSON解析」タブ) |

現状、1〜2のステップ(検出層)は独自の3点マーキング形式
({eyeLeft, eyeRight, mouth}座標)で内部管理しており、ユーザー提示の
JSON Schema(`detection_id` / `detected_feature.abstract_components`
[eyes/hair_line/nose/mouth] / `facing_direction` / `clarity_score` /
`area_attribute.palace_name` / `domain_category`)とは形式が異なる。
3.のステップだけを先行実装し、「抽象相JSON解析」タブでこのJSON形式を
直接貼り付けて実行できるようにした(外部の検出システムの出力を
そのまま流し込むことも、将来的に検出層をこの形式に合わせて拡張する
こともできる)。

### `buildAbstractGansouReport()`の解釈ロジック

- **`location`**(例: `right_cheek`, `forehead`, `eye_corner`,
  `hairline`, `chin`)→ 日本語ラベルに変換(`LOCATION_LABELS`)。
  未知の値はアンダースコアをスペースに置換してそのまま表示。
- **`abstract_components`**(`eyes`/`hair_line`/`nose`/`mouth`の
  4要素、例: `two_dots`, `top_hair_line`, `triangle_nose`,
  `horizontal_line`)→ `COMPONENT_LABELS`で日本語化し、構成要素の
  説明文として結合。
- **`facing_direction`**(`outward`/`inward`/`downward`/`upward`)→
  既存の`ORIENTATION_MEANINGS`(内向き/外向き/上向き/下向き)を
  再利用。**「顔の中心から逆方向=敵対」という発想は`outward`に
  一貫して適用**。
- **`clarity_score`**(0.0〜1.0)→ 3段階のコメント(はっきり/中程度/
  淡い)に変換。
- **`area_attribute.palace_name`**→ 伝統的な**十二宮**
  (命宮・兄弟宮・夫妻宮・子女宮・財帛宮・疾厄宮・遷移宮・奴僕宮・
  官禄宮・田宅宮・福徳宮・父母宮)の意味テーブル`PALACE_MEANINGS`で
  解釈。`palace_name`が無い、または未知の場合は`domain_category`
  (romance/career/interpersonal/health/wealth)から対応する宮を推定
  するフォールバックを実装(例: `romance`→`夫妻宮`)。

### 実行例(ユーザー提示のサンプルJSONで実際に確認済み)

```json
入力: {
  "detection_id": "det-0001",
  "detected_feature": {
    "location": "right_cheek",
    "abstract_components": { "eyes": "two_dots", "hair_line": "top_hair_line", "nose": "triangle_nose", "mouth": "horizontal_line" },
    "facing_direction": "outward",
    "clarity_score": 0.72
  },
  "area_attribute": { "palace_name": "夫妻宮", "domain_category": "romance" }
}

出力メッセージ: 「右頬」(夫妻宮)に検出された抽象的な隠れ相は、向き(外向き)
から見て対外的な反発や敵対心を示すとされます。ある程度はっきりした、中程度
の鮮明さのパターンです。あくまで伝統的な言い伝え・娯楽的な解釈であり、実際
の心理状態や人間関係を断定するものではありません。
```

`palace_name`を省略し`domain_category: "career"`のみを渡した場合も、
`官禄宮`に自動フォールバックすることをNode上のユニットテストで確認済み。
未知の`location`・空の`abstract_components`・`area_attribute`省略といった
欠損の多い入力でもエラーにならず適切なフォールバック文言を返すことも
確認済み。



率直な評価: **直接のデータ再利用はほぼ無いが、概念的な設計は再利用できている。**

- 辞書(PARTS)は「実在する顔のパーツ(眼・鼻・眉…)の伝統的な文献解釈」
  であり、願相(画像の中に偶然浮かび上がる“もう一つの顔”)とは
  **観察対象そのものが別物**。眼のデータをいくら増やしても、願相の
  検出・解釈には直接使えない。
- ただし、`data/eyes.js`の`eye_twelve_palace_mapping_method`
  (眼球の周囲に十二宮を対応させる観法)や
  `red_vein_palace_position_collection`(位置ごとに意味づけを変える
  という考え方)は、まさに今回の`POSITION_MEANINGS`と**同じ構造の
  発想**(顔の位置によって意味が変わる、という伝統的な相学の型)。
  つまり、辞書作りを通じて「相法は位置ベースで意味づけをする体系が
  多い」という設計パターンを学べたことが、今回のエンジン設計に
  活きている。
- 実利用面でも接点はある: カルテ機能(`docs/KARTE_DESIGN.md`)は
  人物単位で観察記録を蓄積する設計なので、将来的には同じカルテに
  「辞書からの記録」と「願相の検出記録」を**両方**紐づけることができる
  (例: ある人物のカルテに、実際の目の相の記録と、その人の写真から
  検出された願相の記録を並べて見られるようにする、など)。今回は
  ここまでは実装していないが、データモデル上は無理なく拡張できる。

**結論**: 辞書データそのものはこの機能の直接の燃料にはならないが、
「位置に意味を持たせる」という設計思想の土台として活きており、
今後カルテ機能で両者を統合していく余地は十分にある。


## 全体解析(自律・選択操作なし)モード(`app/autonomous-face-reader.js`、今回追加)

ユーザーから「目・口・眉等をプルダウンで選択させる方式は採用せず、写真を
アップロードするだけでAIが自律的に隠れ相(潜在的な表情・象徴・心理的
ニュアンス)を探索・抽出してほしい」という要望が提示された。これに対応する
新しい4つ目の検出方式として`app/autonomous-face-reader.js`を追加した
(隠れ相タブに「全体解析(自律・選択操作なし)」モードとして実装)。

### この機能が実際にやっていること

画像アップロード後、ユーザーの追加操作なしに(ボタン1つ押す必要すらなく、
ファイル選択だけで)以下を自動計算し、伝統的な相学・色彩心理のような
発想枠で言語化する:

- **明るさ**(画面全体の平均輝度)→ 気分の明暗の代理指標
- **色味**(赤み/青みのバランス)・**彩度** → 色彩心理の代理指標
- **左右対称性**(画像を鏡映して左右半分を比較した差分)→ 内面の葛藤・
  複数の側面の代理指標
- **光の当たり方**(上下左右どちらが明るいか)→ 内向き/外向き・
  理想志向/現実志向の代理指標
- **明暗の起伏**(隣接画素の勾配の平均。エッジの多さ)→ 緊張感・
  活発さの代理指標

これらはすべて`app/hidden-face-detector.js`とは異なるアプローチである点に
注意: 検出層(`hidden-face-detector.js`)は「画像のどこかにある点+線の
パターン(顔らしい局所パターン)」を探すのに対し、こちらは位置を問わず
**画像全体**の大づかみな特徴だけを見る。ユーザー要望にあった「パーツ選択
方式を採用しない」という制約を満たすため、あえて局所パーツの検出・選択を
経由しない設計にしている。

### ★正直な注意(できていないこと)

ユーザー要望にあった以下の項目は、字義通りには実装できていない
(実装にはオフラインでは用意できていない専用MLモデルが必要なため):

- **表情筋の微細な動き**: 表情推定(facial action unit検出)には専用の
  MLモデルが必要。未実装。
- **視線の方向と強度**: 視線推定(gaze estimation)には専用のMLモデルが
  必要。未実装。
- **顔の左右差(パーツ単位の精密な非対称性)**: 実装しているのは画像
  全体を鏡映して比較する大づかみな代理指標であり、目・口といった
  パーツ単位の精密な非対称性検出ではない。
- **顔のパーツ間のバランス**: パーツそのものを検出していないため未実装。

実装したのは、あくまで画像全体のピクセル値(明るさ・色・彩度・左右差・
起伏)という「大づかみな画像特徴」からの類推であり、これを結果メッセージ
の末尾に必ず明記している(`AutonomousFaceReader.LIMITATION_NOTE`)。
将来的に本格的な顔ランドマーク検出・視線推定を組み込む場合は、上記の
「将来、本当にAIモデル化する場合のロードマップ」の技術スタック案
(YOLOv8/OpenCV等)に、表情筋・視線推定用の追加モデル(例:
MediaPipe Face Mesh、OpenCVのdnnモジュール等)を組み合わせる形が
現実的だが、これも未着手。

### テスト

`tests/autonomous-face-reader.test.js`(`npm test`で実行可能)で、
合成データを使い以下を確認済み:

- 暗い/明るい均一画像で明るさの判定が変わること
- 暖色/寒色寄りの画像で色味の判定が変わること
- 左右非対称な画像(片側が明るい)で対称性スコア・光の左右差が
  正しく検出されること
- 0×0の空画像でもクラッシュしないこと
- 出力メッセージに必ず限界注記(表情筋・視線を検出していない旨)が
  含まれること

## 検出層(`app/hidden-face-detector.js`)可能性拡張版(今回追加)

ユーザーから「顔の写真など(=顔写真に限らず)で隠れた顔を認識する技術の
可能性を高めてほしい」という要望が出たことを受け、検出層(点+線パターン
探索)に以下3点を追加した:

1. **真の局所適応閾値(局所標準偏差)**: 従来は「どれだけ暗ければ暗いと
   みなすか」の基準(標準偏差)が画像全体で1つの値だったが、これも
   積分画像(2乗和)を使って局所計算するようにした(Niblack/Sauvola系の
   二値化に近い方式)。明暗のコントラストが場所によって大きく異なる写真
   (例: 一部は平坦、一部は複雑な木目や岩肌)でも、それぞれの領域に応じた
   基準で検出できるようになった。平坦な領域で標準偏差が0に近づき過検出に
   ならないよう、画像全体の標準偏差の30%を下限にしている。
2. **肌色マスキングの明示的なON/OFF切り替え(UI追加)**: 肌色マスキングは
   実在の顔写真向けの機能で、木目・岩肌・壁のシミ・雲などの一般的な
   パレイドリア探索ではむしろ検出範囲を狭めてしまう。「画像マーキング」
   モードにチェックボックスを追加し、ユーザーが用途に応じてON/OFFを
   選べるようにした(既定はON=顔写真向け)。
3. **マルチスケール探索(`findFaceCandidatesMultiScale`)**: Canvas APIに
   依存しない純粋なJS実装のボックス平均法縮小(`resizeImageDataBoxAverage`、
   Node上でもテスト可能)で複数解像度(既定160/240/360px)のバージョンを
   作り、それぞれで探索してから元画像の座標系に統合する。1つの解像度では
   縮小しすぎて潰れる/大きすぎてノイズに弱い、といった見逃しを別の解像度で
   拾える可能性を上げる。UIの「自動検出する」ボタンはこの関数を使うように
   更新した。

いずれも合成データでのユニットテストを追加済み(`tests/hidden-face-
detector.test.js`、局所標準偏差の挙動・縮小関数の正しさ・マルチスケール
探索の座標変換・肌色マスキングOFF時の非肌色画像での検出、を確認)。

**正直な注意**: これらもすべて古典的画像処理の改善であり、機械学習モデル
ではない。マルチスケール探索は処理コストが解像度の数だけ増える
(既定3解像度)。実写真・実際の木目や岩肌の写真での検証はまだ行っていない
(引き続き合成データでのテストのみ)。

## 意味づけの出典についての正直な監査結果(今回・2026-08セッションで追加)

ユーザーから「願相(隠れ相)機能の意味づけは、これまでに`data/`へ入力した
文献データに基づいているか？ 違うなら勝手に意味を作らないでほしい」という
指摘があり、`app/hidden-face-engine.js` と `app/autonomous-face-reader.js`
の意味づけ文を全て監査した。結論:

**`data/`(PDF文献から出典付きで採録した262項目)には基づいていない。**
以下がその根拠:

1. `hidden-face-engine.js` と `autonomous-face-reader.js` は、コード上
   `data/index.js` の `PARTS` 配列を一切 `require`・参照していない
   (`app/app.js` の辞典/カルテタブだけが `PARTS` を使っている)。
2. `POSITION_MEANINGS` / `ORIENTATION_MEANINGS` / `TYPE_MEANINGS` /
   `PALACE_MEANINGS`(`hidden-face-engine.js`)や、明るさ・色味・彩度・
   左右差・光の当たり方の意味づけ(`autonomous-face-reader.js`)は、
   いずれも過去セッションで「ユーザー提示の願相検出プロンプト」という
   アイデアを元に、このアプリが独自に組み立てた解釈フレームワーク。
3. 「涙堂」「十二宮」など、伝統的な人相学の用語自体は借用しているが、
   意味づけの中身は文献記述と照合されていなかった。実例として、
   `data/eyes.js` の `tianzhai_eyelid_area_meaning`(田宅=眉と眼の間)
   は文献上「田地・家宅・目上運」の暗示と記録されているのに対し、
   旧版の `hidden-face-engine.js` の `POSITION_MEANINGS['右目の下']` は
   「感情面・直近の心配事」としており、同じ部位でも中身が食い違って
   いた。
4. 出力メッセージも旧版では「あくまで伝統的な言い伝え・娯楽的な解釈」
   「色彩心理の伝統的な見立てです」のように、あたかも古典文献に基づく
   かのような表現になっていた。

### 今回行った対応

- `POSITION_MEANINGS` / `ORIENTATION_MEANINGS` の各説明文、および
  `buildGansouReport` / `buildAbstractGansouReport` の出力メッセージから
  「伝統的な言い伝え」という表現を削除し、「本アプリ独自の解釈枠組みで
  あり、文献データに基づくものではない」という趣旨に統一した。
- `autonomous-face-reader.js` 側も同様に「色彩心理の伝統的な見立て」
  等の表現を「本アプリ独自の見立て(文献上の裏付けはない)」に修正した。
- 両ファイルの冒頭コメントに出典についての注記を追加し、今後この種の
  意味づけを追加・拡張する際の方針(文献に基づくかのような表現は使わず、
  独自解釈であることを明記する。文献に基づく意味づけを追加したい場合は
  `data/`側に出典付きでデータ化するのが筋で、このファイルに直接
  書き込むべきではない)を明記した。
- 機能(スコア計算・向き判定・検出ロジックそのもの)は変更していない。
  変更したのはあくまで「意味づけ文の出典表示」の正確性のみ。
- テスト1件(`tests/hidden-face-engine.test.js` の免責文言チェック)を
  新しい文言に合わせて更新し、`npm test` 全件成功を確認済み
  (合計19+12+20件、既存の検出層・全体解析テストと合わせてグリーン)。

### 位置(部位)を限定せず全体から拾ってほしいという要望について

検出層(`hidden-face-detector.js` の `findFaceCandidates` /
`findFaceCandidatesMultiScale`)自体はもともと部位名に依存しない
純粋なピクセル解析で、画像のどこにあっても点+線パターンを探す設計に
なっている(コード上、位置ラベルへの参照なし)。一方、**解釈層**の
`POSITION_MEANINGS`(6項目)や `LOCATION_LABELS`(9項目)は固定の
少数リストしか用意していない。今回はこれを文献データが無いまま
無理に拡張することはせず(=「違うならば勝手に入れないでほしい」という
指示を優先)、リストに無い位置は「この位置に対応する意味づけ(本アプリ
独自の解釈枠組み)は登録されていません。参考程度に留めてください」と
正直にフォールバックする既存の挙動をそのまま維持した。部位を問わず
網羅的に位置ラベル・意味づけを拡充したい場合は、次回以降ユーザーと
方針(独自解釈のまま拡張するのか、文献裏付けのある意味づけだけに
絞るのか)を確認してから進めるのがよい。
